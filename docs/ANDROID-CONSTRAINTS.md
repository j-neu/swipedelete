### Decision

**`MAX_GRANTS = 20` stands — but reclassified as a product/UX cap, not an OS-derived limit.** The OS grants far more headroom than 20: **512** persisted grants per app per user on API 30+ and **128** on API 26–29. Twenty is therefore never forced by the platform and never reaches the point where the OS would evict anything; the binding constraint is the app's own UI budget. The value 20 remains defensible as **5 destination slots (the five footer folders, `docs/SPEC.md:170`) plus 15 source slots**, which keeps onboarding, the grant list, and one-tap revoke bounded while leaving ~2.5× headroom over the tightest (API 26–29) OS budget. Because the platform enforces no limit at 20, `SourceGrantRepository` must enforce `MAX_GRANTS = 20` itself and return `GrantCapReached` when exceeded (as Task 25/M0-T16 already specifies) — the platform will not do it. The plan's "evaluate `takePersistableUriPermission` limits on low-end devices" concern is answered for the OS limit (128 is the low-end floor, comfortably above 20); only the 20-grant durability check remains pending. **No amendment to 20 is made by this task.**

### Failure mode

What actually happens when the platform cap is exceeded: **silent eviction of the oldest persisted grants for that app**, not an exception and not unbounded growth. On API 30+ the 513th grant causes the least-recently-*created* persisted grants to be released until 512 remain; on API 26–29 the same happens above 128. The app loses read/write access to the evicted folder with no callback and no error — a later access simply fails with `SecurityException`/`FileNotFoundException` from the provider, which is the dangerous, hard-to-attribute case. The separate, non-cap failure is `SecurityException("No persistable permission grants found for UID ...")` thrown by `takePersistableUriPermission` when the URI was never offered a persistable grant (or its transient grant has expired). **Mitigation (already the M0-T16 design, sharpened here):** (1) surface the count and the cap in the grant UI ("14 of 20 slots used") so the limit is never invisible; (2) offer one-tap revoke of the oldest/least-used grant so the user makes room explicitly *before* the app would need to — relying on OS eviction is not acceptable because it is silent and unordered from the user's perspective; (3) wrap every `takePersistableUriPermission` call in a `try/catch (SecurityException)` and treat failure as "slot not granted", never as success; (4) verify after persisting that the grant is present in `getPersistedUriPermissions()`. At `MAX_GRANTS = 20` the app's own cap fires long before the platform's, so this failure mode is a hypothesis to test, not a risk the shipped app should ever encounter.

### Decision

**Quarantine root: `context.getExternalFilesDir(null)` (the primary volume), unchanged from decision 7 — with two amendments to how Task 17 must use it.**

Answer to the brief's three cases, separately:

**(a) Raw filesystem source → quarantine target, same mount — O(1) rename, use it.** When the source is a raw path the app can name (Tier 2 All Files Access, an app-owned directory, or any other local path on the same volume as the quarantine root), a same-mount rename is a single `rename(2)` directory-entry operation: no file bytes are read or written and the cost does not scale with file size. This holds at every API level the app supports (`minSdk 26`); what the API level changes is only the Java surface, not the kernel semantics. Task 17 should attempt it with `Files.move(source, target, StandardCopyOption.ATOMIC_MOVE)` (available since API 26) rather than `File.renameTo`, because `ATOMIC_MOVE` converts the cross-device case into the single, precise, catchable `AtomicMoveNotSupportedException` (row 4), whereas `renameTo` only returns `false` (row 3) and gives no reason.

**(b) SAF source → quarantine target — always the copy path; there is no SAF rename into quarantine.** `DocumentsContract.renameDocument` (API 21) only renames a document within its current parent, and `moveDocument`/`copyDocument` (API 24) only operate within one document provider and carry no O(1) guarantee; more decisively, the quarantine directory is under `Android/data/`, which is excluded from `ACTION_OPEN_DOCUMENT_TREE` on API 30+, so no target `Uri` exists to move into (row 7). SAF sources are therefore read with `ContentResolver.openInputStream(uri)` and go straight to the copy fallback. SAF capability flags (`FLAG_SUPPORTS_RENAME` / `FLAG_SUPPORTS_MOVE` / `FLAG_SUPPORTS_COPY`) are irrelevant to quarantine and must not be probed for it.

**(c) App external files dir as target — same mount as the rest of `/storage/emulated/0`; a different mount from a removable volume.** `getExternalFilesDir(null)` is `/storage/emulated/0/Android/data/<pkg>/files` on the primary emulated volume (row 8), so a raw source anywhere else on `/storage/emulated/0` shares its mount and the rename is O(1). `getExternalFilesDirs(null)` returns `[0]` = that primary path (row 9); any removable media appears at `[1..]` as `/storage/XXXX-XXXX/Android/data/<pkg>/files`, a separate mount. Therefore: **quarantining a file that lives on the removable card into the primary quarantine root is cross-volume and always takes the copy fallback**, and a raw rename into a *removable* quarantine root from a primary source is likewise cross-volume. Keep the single primary quarantine root (decision 7) so the common case is same-volume; do not silently switch roots.

**Net confirmation for Task 17:** the plan's "same-volume rename first, else copy" strategy is correct, but "same-volume rename" is available **only for raw-path sources on the primary volume**, and the two non-raw source kinds must be treated differently:

- **SAF sources always take the copy fallback — established, not assumed.** A SAF source is addressed by a granted content URI, and the platform contract provides access only through `ContentResolver`/`DocumentsContract` on that URI, with no API that maps a document URI to a filesystem path (row 10). No same-mount rename exists for it.
- **MediaStore sources: routing is an explicit assumption to be confirmed by V4, not a fact established here.** The Android reference directs apps to open media items with `ContentResolver.openFileDescriptor(Uri, …)` and says not to construct a raw path from `RELATIVE_PATH`, and `DATA` is deprecated and read-only for apps targeting Android 11+; however Android 11+ FUSE does restore direct-file-path access for permitted files (row 11). Task 17 must not hard-code "MediaStore ⇒ copy" on this note's authority alone. V4 owns the per-API MediaStore mechanism and must either confirm the copy path or identify a supported raw-path route.

Either way, SAF and MediaStore content-URI sources are the common case, not the exception, so the fallback must be a first-class, fully cancellable, verifying implementation, not an edge-case handler.

### Fallback

**Exact failure signal to catch (and only that).** Catch `java.nio.file.AtomicMoveNotSupportedException` from the `ATOMIC_MOVE` attempt. Do **not** catch a broad `Exception` to decide "cross-device": under the hood the kernel error is `EXDEV` (row 2), but the JVM surfaces a different `FileStore` precisely as `AtomicMoveNotSupportedException`; a `false` return from `renameTo` is the only other cross-device signal (row 3). A SAF provider that does not support an operation has no dedicated exception — it surfaces as `FileNotFoundException` / `RemoteException` / `SecurityException` / `IllegalArgumentException` and must be handled as "unsupported", never as "cross-device". Any other `IOException` (permissions, ENOSPC, I/O error) is a hard failure that aborts the item and leaves the original untouched — it must not be retried as a copy.

**Fallback sequence (copy → verify → delete original), ordered so the original is the last thing touched:**

1. **Space pre-flight (copy path only).** A rename consumes only a directory entry; the fallback consumes a full second copy, so require `quarantineRoot.usableSpace ≥ item.size` (plus a small headroom) *before* copying. On shortfall return `QuarantineResult.InsufficientSpace(neededBytes, freeBytes)` (already in the M0-T02 contract). Do not partially start a copy. This is the "quarantining a 4 GB video needs 4 GB free" requirement from `docs/SPEC.md:293`; the same-volume rename path needs no pre-flight.
2. **Copy to a temp file in the destination batch directory** (`<root>/<batchId>/<originalRelativePath>.part`): stream source → temp in bounded chunks, computing the SHA-256 of the source bytes and the byte count as they pass. Raw sources use `FileInputStream`; SAF/MediaStore sources use `ContentResolver.openInputStream(uri)`. The temp name is inside the batch dir so the final promotion in step 4 is a same-directory, same-volume rename.
3. **Cancellation at any chunk boundary leaves the original untouched (AC-15).** The cancellation signal is checked at every read/write chunk boundary. On cancellation: stop, close and delete the `.part` temp, and return without touching the original. Because the original is only deleted in step 5, cancelling anywhere in steps 1–4 leaves the original exactly as it was. This is the guarantee `docs/tasks.md:467` (`cancelled quarantine leaves the original untouched`) tests.
4. **Verify before promoting.** The copy is complete only if byte count equals the source size and the re-read SHA-256 of the sealed `.part` file equals the SHA-256 computed from the source stream (and, where the source is MediaStore-indexed, equals the sidecar's recorded size). On any mismatch: delete the `.part` temp, abort the item, leave the original untouched. Never promote an unverified copy. Then atomically rename `.part` → final `<root>/<batchId>/<originalRelativePath>` (same directory, so this rename cannot be cross-device).
5. **Delete the original last.** Only after the verified file is in place at its final quarantine path is the original removed (raw delete, or the MediaStore/SAF delete appropriate to the source, per V4). If the process dies between step 4 and this delete, both the original and the quarantine copy exist — a duplicated item, never a lost one — and the journal identifies which of the two states the item is in so the M0-T09 `Reconciler` can resolve it. If the original delete fails, report the item as failed-with-copy-present; do not delete the quarantine copy.

**Invariant to assert in Task 17's tests:** at every observable point and after any cancellation or crash, the item exists either at its original location or as a *verified* entry in quarantine — never neither, and never only as a partial copy.

### Decision (Q1) — how the index stops showing a ghost, per band

The bytes are quarantined **first** (copy → verify, per V3); only then is the index touched. The exact call per band:

| API band | Exact call that clears the ghost | System confirmation dialog? | What it does to the bytes |
|---|---|---|---|
| **26–28** (legacy, pre-consent) | `contentResolver.delete(rowUri, null, null)` on the stale `Images.Media` / `Video.Media` / `Audio.Media` item. | **No** system dialog exists at this band. Requires `WRITE_EXTERNAL_STORAGE`; without it the delete is refused with `SecurityException` and there is no way to complete or to ask. | Deletes the row; the provider also tries to delete the file at the old `DATA` path, which is already gone, and `deleteIfAllowed` logs-and-continues, so the row is still removed. In effect index-only, because the app removed the bytes in the preceding step. |
| **29** | `contentResolver.delete(rowUri, null, null)`. If the app holds write, it succeeds. If it holds only read, catch `RecoverableSecurityException` and launch `e.userAction.actionIntent` with `startIntentSenderForResult`; on `RESULT_OK` retry the delete. | **Only when the app does not hold write.** One prompt for the item (the API-29 action is a per-item write grant). | Deletes row **and** file. Because the verified quarantine copy already exists, this is the "delete the original last" step of V3's fallback, not a separate reconciliation. |
| **30+ and 33+** (the two bands share one mechanism) | If `OWNER_PACKAGE_NAME` is the app's own package: direct `contentResolver.delete(rowUri, null, null)`, no prompt. Otherwise: `MediaStore.createDeleteRequest(resolver, listOf(rowUri))` → `startIntentSenderForResult(pendingIntent.intentSender, …)`; the OS then calls `ContentResolver.delete` itself. Alternatively `MediaStore.createWriteRequest` first, then direct `delete`/`update`. | **Yes — one OS prompt per batch.** `createDeleteRequest` and `createWriteRequest` are PendingIntent dialogs; the app cannot make a silent MediaStore change to another app's media at this band without All Files Access (forbidden for media). Maximum **2000 uris** per request at `targetSdk` 36. | Deletes row **and** file permanently (delete request), or after a write grant. Bytes were already copied to quarantine, so the user-visible result is "gone from the gallery, restorable from quarantine". |

**Explicitly rejected mechanisms.**

- **`MediaScannerConnection.scanFile`** — it is documented as a way to *add* a file to the provider, its result is asynchronous, and scanning the old path after a rename is not a documented removal contract. The broadcast form (`ACTION_MEDIA_SCANNER_SCAN_FILE`) was deprecated at API 29. Do not use it for reconciliation.
- **`IS_PENDING`** — owner-scoped ("still being inserted by its owner"), 7-day expiry, and setting it on media the app does not own needs the same write consent as any other update. It is an insert lifecycle, not a hide/un-index switch for another app's media.
- **`MediaStore.createTrashRequest`** — it only sets `IS_TRASHED`; the bytes stay at the original path and the OS auto-deletes them after `DATE_EXPIRES` (typically 30 days). It is the reversible OS-managed fallback in `docs/SPEC.md:186`, **not** quarantine reconciliation. Using it *in addition to* a verified quarantine copy would leave two copies and let the OS delete one on its own schedule.
- **Updating `RELATIVE_PATH`** — this would move the file through MediaStore, but the target must be a media-relevant top-level directory and `Android/data/...` is not one, so it cannot move a file into the quarantine root. It also needs write consent.

### Decision (Q2) — rename or copy, per band (this resolves V3's deferred assumption)

**Baseline fact:** the quarantine target is the primary-volume app-external dir (V3, case (c)), so only a source on the same volume could ever be renamed (V3's `EXDEV` / `AtomicMoveNotSupportedException` contract applies unchanged).

| API band | Rename or copy? | Conditions (permission held, MIME class, volume) |
|---|---|---|
| **26–28** | **Same-volume rename is available** (the only MediaStore band where it is). | Requires `WRITE_EXTERNAL_STORAGE` (legacy shared-storage write; no All Files Access needed) **and** the source on the same volume as the quarantine root. MIME class is irrelevant — on ≤28 `WRITE_EXTERNAL_STORAGE` covers images, video and audio alike. Use `Files.move(src, dst, ATOMIC_MOVE)` per V3; on `AtomicMoveNotSupportedException`/`EXDEV` fall back to copy. If the app holds only read, it cannot rename **or delete**, so media quarantine cannot complete at this band without the write permission. |
| **29** | **Copy only.** | Scoped storage removes direct file-path access for every MIME class, and `requestLegacyExternalStorage` is ignored because `targetSdk` is 36. Read via `ContentResolver.openInputStream(uri)` (`READ_EXTERNAL_STORAGE`), verify, then delete the original per Q1 (consent may be required). Volume is irrelevant — a copy is used regardless. |
| **30+** | **Copy for media the app does not own** (the common case); a same-volume rename is possible **only for media the app owns**. | FUSE gives direct-path read of other apps' media with `READ_EXTERNAL_STORAGE` (≤32) or `READ_MEDIA_*` (33+), but write access to another app's media requires user consent or All Files Access (policy-forbidden for media). `WRITE_EXTERNAL_STORAGE` is a no-op at this target. Owned media (`OWNER_PACKAGE_NAME` == the app's package) is writable without a prompt and may be renamed if on the same volume; ownership is best-effort and must default to "not owned" when `NULL`/invisible (API 34+ package visibility). MIME class only changes *which read grant* is needed. |
| **33+** | **Copy (same as 30+).** | No mechanism change: identical calls, only granular `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO` / `READ_MEDIA_AUDIO` read grants. There is no new rename route. |
| **all bands** | Cross-volume → **copy**, always. | Same-volume is necessary for any O(1) rename; a MediaStore item on a removable volume is cross-volume from the primary quarantine root and takes V3's fallback. |

**Net answer to V3's deferred assumption:** **MediaStore is not "always copy" and not "always rename".** It is rename-capable **only on API 26–28 with `WRITE_EXTERNAL_STORAGE` on the same volume**; on every other band (29, 30+, 33+) it is **copy**, and on 30+ the policy ban on All Files Access for media is what closes the raw-write route. Task 17 may therefore keep its single `ATOMIC_MOVE`-then-copy skeleton and gate the fast path on `(Build.VERSION.SDK_INT <= 28 && hasLegacyWrite)`, not on source kind alone.

### All Files Access interaction (constraint that must not be violated)

On API 30+ the only way to obtain silent raw-path **write** access to another app's media is `MANAGE_EXTERNAL_STORAGE`. `docs/SPEC.md:131` (condition 2) forbids using All Files Access to read or edit media, and Play lists "Media Files access" as an invalid use of that permission. V4 therefore records: **the raw-path rename route for MediaStore media on API 30+ is not usable, and must not be implemented behind the Tier-2 capability.** Even when All Files Access is held, `MediaStoreStorageGateway` must keep serving media (AC-10 prevents a media MIME type from being classified as non-media, and the raw gateway is for non-media only). On API 26–28 the raw route requires `WRITE_EXTERNAL_STORAGE`, which is a different permission and is *not* All Files Access, so it remains permitted there.

### Reconciliation is not deletion — and on every band the two cannot be separated

Deleting the MediaStore row destroys the file: the public API has no index-only delete, the one hidden escape (`deletedata=false`) is `@hide` and is ignored for external apps targeting above API 34. `createTrashRequest` is the only operation that hides without destroying, but it does not move the bytes and the OS purges them after `DATE_EXPIRES`. Consequences the downstream tasks must honour:

1. **Order is not negotiable.** Copy → verify SHA-256 + size → then delete the original/row. Deleting the row first would destroy the user's only copy. This is V3's fallback ordering, and V4 confirms there is no cheaper "un-index then move" variant.
2. **For MediaStore sources the destructive step and the reconciliation step are the same call.** There is no separate "fix the index afterwards" call to write for MediaStore. On API 30+ that call is user-confirmation-gated, so quarantining an indexed item is **not silent** above API 29.
3. **Declined consent is a first-class outcome, not an error to retry.** If the user dismisses the `createDeleteRequest`/`createWriteRequest` prompt, the bytes remain both at the original location and in quarantine. Report it as a copy-present failure (the M0-T09 `Reconciler` already distinguishes "both exist" from "lost"); never delete the quarantine copy to tidy up, and never retry the dialog in a loop.

### Downstream impact (confirms/amends Task 17 and Task 20)

- **Task 17 (`QuarantineStore` / M0-T08).** Keep the V3 skeleton. The MediaStore branch is: `SDK_INT <= 28` and legacy write held → `ATOMIC_MOVE` rename then `delete(rowUri)`; otherwise → `openInputStream` copy → verify → delete. On API 30+ the final delete is `MediaStore.createDeleteRequest` (or a preceding `createWriteRequest`), surfaced to the UI as a confirmation, with the declined-consent outcome above. Restore must re-`insert` the MediaStore row (V3's sidecar already records the MediaStore ID, size and MIME), and must not assume the old `_ID` is still free.
- **Task 20 (`MediaStoreStorageGateway` / M1-T01).** The gateway must expose no "un-index" operation, and `quarantine`/`deletePermanently` must branch by band exactly as Q1 states. `deletePermanently` maps to `createDeleteRequest` with chunks of ≤2000 uris, matching V5's scope. `watch()`'s `ContentObserver` will fire when the consent-gated delete completes, so the deck must tolerate the row disappearing mid-session (AC-8).
- **Manifest gap (recommends an amendment to Task 22, M0-T13).** `docs/tasks.md:869` currently declares only `READ_MEDIA_IMAGES`, `READ_MEDIA_VIDEO` and `MANAGE_EXTERNAL_STORAGE`. To make this decision runnable it also needs `READ_EXTERNAL_STORAGE` (with `android:maxSdkVersion="32"`) for API 26–32 media reads, and `WRITE_EXTERNAL_STORAGE` (with `android:maxSdkVersion="29"`) for API 26–29 deletes — **without the latter, MediaStore media quarantine cannot complete on API 26–28 at all, because no consent flow exists there.** Audio decks additionally need `READ_MEDIA_AUDIO` on API 33+. These are normal, Play-legal permissions and are not All Files Access.

### Decision

**(a) Maximum URIs per `createDeleteRequest` and the exact exception.** The spec's **2000 is correct as written** for this app. The maximum is **2000 URIs per request**, and more than 2000 throws **`java.lang.IllegalArgumentException` with the message `URI list restricted to 2000 per request`**, thrown synchronously by the `createDeleteRequest` call itself. Two conditions make it live: the app must `targetSdk ≥ 36` (ours is 36) and the compat change `LIMIT_CREATE_REQUEST_URIS` (203408344L) must be enabled; both hold. The same cap applies to `createWriteRequest`, `createTrashRequest` and `createFavoriteRequest` (one shared `createRequest`). **Do not rely on a device-side rejection to enforce this** — the check is part of the Android 16 MediaProvider and is not present on older provider builds, so a too-large batch could behave differently across devices. The client must chunk.

**(b) Chunking constant to implement.** **`MEDIASTORE_REQUEST_URI_CHUNK = 500`** — see *Chunking constant* below for the exact home.

**(c) `createTrashRequest` availability and auto-purge.** Availability: **API 30 (Android 11) and later only**; there is no trash path on API 26–29. Auto-purge: trashed items carry `DATE_EXPIRES = now + 30 days` (the default), and the provider purges them from `onIdleMaintenance` → `deleteOrExtendExpiredItems`. **Purge is best-effort, not guaranteed:** it runs only when the OS schedules idle maintenance, it never fires for a volume that is unmounted, and an item that expired more than a week ago is extended by 7 days and retried rather than deleted. The app is not notified and can only observe the row disappearing by re-querying; the app cannot cancel or defer a purge. This is exactly why trash is the *weaker* guarantee of spec §4.7 #2 and must be presented to the user as "the OS may delete this on its own schedule, typically ~30 days — this is not our quarantine".

**(d) Trashed bytes, row, listing and un-trash.** While trashed the **bytes stay on the same volume in the same directory**, renamed to `.trashed-<expiryEpochSeconds>-<displayName>`; the `DATA` path is updated, the **row remains** with `IS_TRASHED = 1` and `DATE_EXPIRES` set, and it is hidden from default app queries (`MATCH_EXCLUDE`) until the app passes `QUERY_ARG_MATCH_TRASHED = MATCH_INCLUDE`. The app **can list** its trashed rows this way, and **can un-trash** them with `createTrashRequest(resolver, uris, false)` (another system prompt); because the bytes never moved, restore renames the file back out of the `.trashed-` prefix with **no copy**. Caveat: reading the *bytes* of a trashed item requires ownership (`IllegalStateException("Only owner is able to interact with pending/trashed item …")` otherwise), but the restore path is a metadata flip and does not need the bytes.

**V4 consistency (no silent override).** This note does not contradict V4. V4's row 3 said `createTrashRequest` "does not delete or move the bytes" and the file "stays at its original path"; V5 amends only the precision of "original path" — the bytes are not copied and remain in the same directory/volume, but the file is **renamed in place** to a `.trashed-…` name and the row's `DATA` changes. V4 rejected trash **as a reconciliation mechanism**, and V5 agrees and does not reopen that: trash here is a **destruction** path only, used per spec §4.7 #2 when quarantine is impossible and the item is MediaStore-indexed on API ≥ 30, with explicit consent to the weaker guarantee. V4's API 30+ "one OS prompt per batch, ≤ 2000 uris" statement is unchanged; V5 supplies the exact exception and the chunk value.

**Confirmation-ladder input (spec §6.6).** For the ladder to match reality: **silent** destructive paths are direct `delete`/`update` of media the app owns (API 30+), legacy `WRITE_EXTERNAL_STORAGE` deletes on API 26–28, and SAF `DocumentsContract.deleteDocument`. **System-dialog-gated** paths are `createDeleteRequest`, `createWriteRequest`, `createTrashRequest` (trash *and* un-trash), `createFavoriteRequest`, and the API 29 `RecoverableSecurityException` user action. Spec §6.6's "Permanent delete — two confirmations" therefore composes as: the app's own first confirmation, then the OS `createDeleteRequest` dialog (which is the second, deliberate one and cannot be tapped away into a swipe). No swipe can reach a system dialog without passing the staging strip and Apply.

### Chunking constant

**Use `MEDIASTORE_REQUEST_URI_CHUNK = 500` for every batched `MediaStore` request, in every caller.**

- It is ≤ the real cap (2000) with **4× headroom**, so it stays valid even if the effective limit tightens, and it leaves room for duplicate or re-tried URIs inside a chunk without ever approaching 2000.
- 500 matches the M1 exit-criterion deck size (`docs/tasks.md:1112`, "a 500-item deck triages end-to-end"), so a full deck's Apply is at most one OS prompt per chunk and a normal batch is a single prompt.
- **Home (single source of truth):** `core/storage/src/main/kotlin/com/swipedelete/core/storage/StorageLimits.kt` — a small `:core:storage` object, e.g.

  ```kotlin
  package com.swipedelete.core.storage

  object StorageLimits {
      /** MediaStore.createDeleteRequest / createWriteRequest / createTrashRequest cap is 2000
       *  per request for targetSdk >= 36 (V5, docs/ANDROID-CONSTRAINTS.md). Chunk with headroom. */
      const val MEDIASTORE_REQUEST_URI_CHUNK = 500
  }
  ```

  `:core:storage` is the module that already owns both consumers — Task 17's `QuarantineStore` (`core/storage/src/main/kotlin/com/swipedelete/core/storage/quarantine/QuarantineStore.kt`, `docs/tasks.md:618`) and Task 20's `MediaStoreStorageGateway` (`docs/tasks.md:1116`) — so both import this one constant and neither re-declares a number. Task 17 (`QuarantineStore.empty`) and M1-T05 (staging Apply) must both chunk by it. This file is **not** created by V5; the owning task writes it (Task 20 is the earliest MediaStore task; Task 17 may define it if it lands first).
- Each chunk is passed to one `create*Request` call and therefore produces **one** OS prompt; the caller must surface a multi-chunk batch as N prompts, not assume one.
