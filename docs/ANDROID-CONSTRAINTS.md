### Decision

**`MAX_GRANTS = 20` stands — but reclassified as a product/UX cap, not an OS-derived limit.** The OS grants far more headroom than 20: **512** persisted grants per app per user on API 30+ and **128** on API 26–29. Twenty is therefore never forced by the platform and never reaches the point where the OS would evict anything; the binding constraint is the app's own UI budget. The value 20 remains defensible as **5 destination slots (the five footer folders, `docs/SPEC.md:170`) plus 15 source slots**, which keeps onboarding, the grant list, and one-tap revoke bounded while leaving ~2.5× headroom over the tightest (API 26–29) OS budget. Because the platform enforces no limit at 20, `SourceGrantRepository` must enforce `MAX_GRANTS = 20` itself and return `GrantCapReached` when exceeded (as Task 25/M0-T16 already specifies) — the platform will not do it. The plan's "evaluate `takePersistableUriPermission` limits on low-end devices" concern is answered for the OS limit (128 is the low-end floor, comfortably above 20); only the 20-grant durability check remains pending. **No amendment to 20 is made by this task.**

### Failure mode

What actually happens when the platform cap is exceeded: **silent eviction of the oldest persisted grants for that app**, not an exception and not unbounded growth. On API 30+ the 513th grant causes the least-recently-*created* persisted grants to be released until 512 remain; on API 26–29 the same happens above 128. The app loses read/write access to the evicted folder with no callback and no error — a later access simply fails with `SecurityException`/`FileNotFoundException` from the provider, which is the dangerous, hard-to-attribute case. The separate, non-cap failure is `SecurityException("No persistable permission grants found for UID ...")` thrown by `takePersistableUriPermission` when the URI was never offered a persistable grant (or its transient grant has expired). **Mitigation (already the M0-T16 design, sharpened here):** (1) surface the count and the cap in the grant UI ("14 of 20 slots used") so the limit is never invisible; (2) offer one-tap revoke of the oldest/least-used grant so the user makes room explicitly *before* the app would need to — relying on OS eviction is not acceptable because it is silent and unordered from the user's perspective; (3) wrap every `takePersistableUriPermission` call in a `try/catch (SecurityException)` and treat failure as "slot not granted", never as success; (4) verify after persisting that the grant is present in `getPersistedUriPermissions()`. At `MAX_GRANTS = 20` the app's own cap fires long before the platform's, so this failure mode is a hypothesis to test, not a risk the shipped app should ever encounter.

### Decision

**Quarantine root: `context.getExternalFilesDir(null)` (the primary volume), unchanged from decision 7 — with two amendments to how Task 17 must use it.**

Answer to the brief's three cases, separately:

**(a) Raw filesystem source → quarantine target, same mount — O(1) rename, use it.** When the source is a raw path the app can name (Tier 2 All Files Access, an app-owned directory, or any other local path on the same volume as the quarantine root), a same-mount rename is a single `rename(2)` directory-entry operation: no file bytes are read or written and the cost does not scale with file size. This holds at every API level the app supports (`minSdk 26`); what the API level changes is only the Java surface, not the kernel semantics. Task 17 should attempt it with `Files.move(source, target, StandardCopyOption.ATOMIC_MOVE)` (available since API 26) rather than `File.renameTo`, because `ATOMIC_MOVE` converts the cross-device case into the single, precise, catchable `AtomicMoveNotSupportedException` (row 4), whereas `renameTo` only returns `false` (row 3) and gives no reason.

**(b) SAF source → quarantine target — always the copy path; there is no SAF rename into quarantine.** `DocumentsContract.renameDocument` (API 21) only renames a document within its current parent, and `moveDocument`/`copyDocument` (API 24) only operate within one document provider and carry no O(1) guarantee; more decisively, the quarantine directory is under `Android/data/`, which is excluded from `ACTION_OPEN_DOCUMENT_TREE` on API 30+, so no target `Uri` exists to move into (row 7). SAF sources are therefore read with `ContentResolver.openInputStream(uri)` and go straight to the copy fallback. SAF capability flags (`FLAG_SUPPORTS_RENAME` / `FLAG_SUPPORTS_MOVE` / `FLAG_SUPPORTS_COPY`) are irrelevant to quarantine and must not be probed for it.

**(c) App external files dir as target — same mount as the rest of `/storage/emulated/0`; a different mount from a removable volume.** `getExternalFilesDir(null)` is `/storage/emulated/0/Android/data/<pkg>/files` on the primary emulated volume (row 9), so a raw source anywhere else on `/storage/emulated/0` shares its mount and the rename is O(1). `getExternalFilesDirs(null)` returns `[0]` = that primary path (row 10); any removable media appears at `[1..]` as `/storage/XXXX-XXXX/Android/data/<pkg>/files`, a separate mount. Therefore: **quarantining a file that lives on the removable card into the primary quarantine root is cross-volume and always takes the copy fallback**, and a raw rename into a *removable* quarantine root from a primary source is likewise cross-volume. Keep the single primary quarantine root (decision 7) so the common case is same-volume; do not silently switch roots.

**Net confirmation for Task 17:** the plan's "same-volume rename first, else copy" strategy is correct, but "same-volume rename" is available **only for raw-path sources on the primary volume**. SAF sources and MediaStore content-URI sources (no raw path under scoped storage) always use the fallback; they are the common case, not the exception. The fallback must therefore be a first-class, fully cancellable, verifying implementation, not an edge-case handler.

### Fallback

**Exact failure signal to catch (and only that).** Catch `java.nio.file.AtomicMoveNotSupportedException` from the `ATOMIC_MOVE` attempt. Do **not** catch a broad `Exception` to decide "cross-device": under the hood the kernel error is `EXDEV` (row 2), but the JVM surfaces a different `FileStore` precisely as `AtomicMoveNotSupportedException`; a `false` return from `renameTo` is the only other cross-device signal (row 3). A SAF provider that does not support an operation has no dedicated exception — it surfaces as `FileNotFoundException` / `RemoteException` / `SecurityException` / `IllegalArgumentException` and must be handled as "unsupported", never as "cross-device". Any other `IOException` (permissions, ENOSPC, I/O error) is a hard failure that aborts the item and leaves the original untouched — it must not be retried as a copy.

**Fallback sequence (copy → verify → delete original), ordered so the original is the last thing touched:**

1. **Space pre-flight (copy path only).** A rename consumes only a directory entry; the fallback consumes a full second copy, so require `quarantineRoot.usableSpace ≥ item.size` (plus a small headroom) *before* copying. On shortfall return `QuarantineResult.InsufficientSpace(neededBytes, freeBytes)` (already in the M0-T02 contract). Do not partially start a copy. This is the "quarantining a 4 GB video needs 4 GB free" requirement from `docs/SPEC.md:293`; the same-volume rename path needs no pre-flight.
2. **Copy to a temp file in the destination batch directory** (`<root>/<batchId>/<originalRelativePath>.part`): stream source → temp in bounded chunks, computing the SHA-256 of the source bytes and the byte count as they pass. Raw sources use `FileInputStream`; SAF/MediaStore sources use `ContentResolver.openInputStream(uri)`. The temp name is inside the batch dir so the final promotion in step 4 is a same-directory, same-volume rename.
3. **Cancellation at any chunk boundary leaves the original untouched (AC-15).** The cancellation signal is checked at every read/write chunk boundary. On cancellation: stop, close and delete the `.part` temp, and return without touching the original. Because the original is only deleted in step 5, cancelling anywhere in steps 1–4 leaves the original exactly as it was. This is the guarantee `docs/tasks.md:467` (`cancelled quarantine leaves the original untouched`) tests.
4. **Verify before promoting.** The copy is complete only if byte count equals the source size and the re-read SHA-256 of the sealed `.part` file equals the SHA-256 computed from the source stream (and, where the source is MediaStore-indexed, equals the sidecar's recorded size). On any mismatch: delete the `.part` temp, abort the item, leave the original untouched. Never promote an unverified copy. Then atomically rename `.part` → final `<root>/<batchId>/<originalRelativePath>` (same directory, so this rename cannot be cross-device).
5. **Delete the original last.** Only after the verified file is in place at its final quarantine path is the original removed (raw delete, or the MediaStore/SAF delete appropriate to the source, per V4). If the process dies between step 4 and this delete, both the original and the quarantine copy exist — a duplicated item, never a lost one — and the journal identifies which of the two states the item is in so the M0-T09 `Reconciler` can resolve it. If the original delete fails, report the item as failed-with-copy-present; do not delete the quarantine copy.

**Invariant to assert in Task 17's tests:** at every observable point and after any cancellation or crash, the item exists either at its original location or as a *verified* entry in quarantine — never neither, and never only as a partial copy.
